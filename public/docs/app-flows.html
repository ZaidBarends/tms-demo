Flow diagrams for the whole built application: its structure, screens, access, data, scheduling rules and presenter tools. Companion to Process flows, which covers the business processes.

1. What this document adds

Process flows explains the business processes: how a deal becomes a class, an invoice and a certificate. This document maps the application itself: how it is structured, how a person moves through its 44 screens, where state lives, what each action writes, how the scheduling and resource rules decide, and how the presenter tools and build pipeline work.

Every number, screen name and role list below was read from the code (access.ts and each area’s extra.screens.ts, the stores, the logic modules and the build scripts), so it describes the app as built, not as planned.

2. Application architecture

The app is a single-page React application with no back end. Everything a person sees is drawn from data in the browser. Six areas of screens sit on a shared foundation, and all state is held in Zustand stores that save themselves to localStorage.

  • One registry drives everything. Each screen is declared once (id, title, area, path, route, roles, release, why). The route table, the side navigation, the guard, Jump to, the Demo map and the Access rules screen all read that list, so they can never disagree.
  • Areas own their logic. Each area folder keeps its screens, its store, its pure logic (with tests) and its stylesheet. Areas share records through the main store, not by importing each other’s screens.
  • The router is hash-based so the built dist folder works from any static host, or straight from disk, with no server rewrites.

4. Routing and the access guard

The demo lets anyone open any address, then protects each screen with a guard. Instead of showing an error, the guard moves the viewer to a persona who can open the screen and says so. This keeps shared links, tours and the Demo map working.

  • The check is a single function: All access passes everything, otherwise the persona must be in the screen’s role list.
  • The side navigation shows only screens marked for menu display whose role list contains the persona (All access borrows the Administrator’s menu).
  • A real product would hide the screen or return “not allowed”; the switch-and-explain behaviour is a deliberate presentation choice.

6. Hand-offs between screens and personas

The app is built so that one person’s action shows up on another person’s screen. Because every area reads from the same store, there is no sync step: the next render simply sees the change.

  • Sales to client and back. A booking request in the client portal creates an Enquiry in Opportunities; the client sees the staff-side stage translated into “Requested” or “Confirmed”.
  • Delivery to learner. Sessions scheduled by the Administrator appear on the Instructor’s schedule; certificates issued on the class list appear on the learner’s My learning.
  • Money to client. Invoices Finance tracks and collects appear on the client’s Our invoices, with the same balances.
  • Talent loop. Opt-in, search, request and approval move between the B2C learner and the recruiter, with every step written to the audit trail the Administrator reads. See Process flows section 8 for the ringfencing rules.

9. Scheduling and resources

Scheduling is where the resource register meets sessions. Three pieces of logic work together: the conflict check (is this session allowed?), the equipment demand rule (how many units does it need?) and the register’s own guards (what may be changed or removed?).

9.1 Conflict check

This full check runs in the session form and when a session is dragged to a new date on the calendar. It compares a session with every other live session on the same day; cancelled sessions are always ignored. The calendar’s red highlights, the Resources screen, the Alert Centre and the bell use a lighter pass over all sessions that looks only at shared venues, shared instructors and overbooked tracked equipment; out-of-service resources and unavailable dates show up in the full check only.

9.2 Equipment demand and stock

A stock of 0 means the item is not tracked (several projectors, say) and can never clash on its own. A tracked item such as “Loan laptops” (16 in stock, per learner) clashes when two sessions on one day together need more than 16.

11. Presenter tools

The demo is built to be presented. Everything a presenter needs sits in the top bar, so a story can be told without leaving the app.

The tour engine

11 tours (Opportunity to invoice; A self-paying learner; Talent connection and ringfencing; An instructor’s day; How access works; Pre- and post-course surveys; A client books training; Needs analysis to quote; Assign and chase compliance; Getting paid; Reschedule or cancel a booking). A tour is just a list of steps, each naming a persona and an address, so it works by driving the same persona switch and router a person would use.

Because a tour only sets the persona and address, it can never show something the app could not; if a step’s screen is wrong for its persona, the guard in Diagram 3 corrects it and says so.

12. Build, run and test

  • No install needed on the demo machine. The batch files put the bundled Node on the PATH for that window only.
  • The build is type-checked first. A type error stops vite build, so dist is never produced from code that does not compile.
  • Relative base path. Vite builds with base: './' and the router is hash-based, so dist can be hosted in any folder.
