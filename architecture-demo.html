Zimele Technologies Learning Platform: Demo Architecture (as built)

Technology, structure, dependencies, data and state design, and build of the application. This is the architecture of the frontend-only demo as built. The planned production design is in Architecture. Companion to App flows and Process flows.

1. Purpose and design principles

This document describes how the Zimele Technologies Learning Platform demo is built: its technology, structure, dependencies, data and state design, and the trade-offs behind them. For how the business works see Process flows; for how a person moves through the screens see App flows.

Facts here were measured from the repository: file and line counts and the import graph come from scanning src/; sizes come from the last build in dist/.

PrincipleWhat it means in the code
Frontend onlyNo back end. Browser storage is the database, seeded from code, so the demo runs anywhere and can be reset.
One source of truth for accessA single screen registry drives routes, navigation, guard, Jump to, Demo map and the access matrix.
Areas are vertical slicesEach area (tms, lms, b2c, talent, admin) owns its screens, store, logic, tests and styles.
Logic is testable without a browserRules live in plain modules; components mostly call them.
Designed to be presentedPersonas, tours, Jump to, explainer and Reset are first-class parts of the shell.

3. Runtime composition

Everything renders inside one React tree. Shell is a layout route: it draws the top bar and side navigation and renders the chosen screen through an outlet. Each screen route is wrapped in a Guard that checks the persona against the screen’s roles before rendering it.

  • The theme is set in two places that stay in step: the Fluent provider (components) and a data-theme attribute on the page (hand-written CSS variables).
  • Overlays that belong to the presenter (tour, welcome, palette, dialogs) are mounted by Shell, so they survive route changes.
  • Screens read data with store selectors, so only components that use a changed value re-render.

6. Screen registration and routing

A screen is added by writing three small things. Everything else is generated from them, which is why the navigation, guard, Jump to, Demo map and access matrix can never disagree.

Roles on a screen are the only access rule. A screen without nav: true is reachable (and guarded) but is not in the menu; it is opened from another screen, such as the course player from My learning.

7. Data model

The main store holds one Data object with 25 record lists. Records refer to each other by string id; there are no object references, which keeps the data serialisable to localStorage and easy to clone.

  • Payer on the enrolment (self, employer, internal) decides ownership: who sees the learner’s history, who is invoiced and whether the learner can ever reach the talent pool.
  • Derived values are not stored. Invoice totals with VAT, seats taken, clashes and alerts are computed from the lists on demand.
  • Area stores hold extras keyed by main-store ids (for example opportunity owner and tasks keyed by opportunity id), so the core records stay small and shared.

8. State management

State is held in Zustand stores. The main store owns the shared business records and the presentation settings. Each area adds its own store for data only that area needs. Every store persists itself and registers a reset hook.

ConcernHow it is handled
Immutable updatesStore actions clone the data (structuredClone), change the clone, then set it. Components never mutate store data.
Pure logic apart from ReactEach area keeps rules in plain modules (logic.ts, calc.ts, stock.ts, ringfence.ts) that tests call without rendering anything.
Registry-driven navigationScreens are declared once with their roles; nav, guard, Jump to, Demo map and Access rules read that list.
Seed in codebuildSeed() builds the whole data set relative to the current date, so dates stay near today; each area store has its own seed function.
Versioned persistenceEvery store has a storage key with a version suffix; changed shapes migrate (the resource register) or bump the key.
One stylesheet per areaA global styles.css plus one CSS file per area, loaded when its code is imported; Fluent supplies component styling and theme tokens.
Money and datesVAT is one constant (15%); date helpers in shared/format.ts work with ISO date strings so sorting and comparison are string-safe.

Because area code often needs to change shared records (a booking changes enrolments, a rename changes sessions), area modules call the main store directly. The talent store, for example, keeps the main store’s placed flag in step with the recruiter pipeline, and the resource actions rename venues across sessions and quotes.

10. Testing architecture

21 test files run under Vitest in a plain Node environment, so they are fast and need no browser. A small localStorage shim lets the persisted stores run.

LayerCoversTechnique
Pure logicpricing, ringfencing, stock and clashes, money calculations, survey rules, gamification, skills, client rulesDirect function calls, no DOM
Store actionshand-offs between ops and the main store, resource register actions, survey and talent storesReal stores with an in-memory localStorage shim
Renderingevery screen for every persona, plus focused render tests for ops, money and surveysreact-dom/server renderToString inside a MemoryRouter
Registry integritytours reference real screens and personasPlain assertions over the registry

The smoke test is the safety net for the registry design: because every screen is in one list, one loop renders each screen as each persona and fails if any of them crashes.

11. Architectural observations

What the code shows, why it matters, and the smallest change that would improve it. None of these stop the demo working; they are the places to look first if it grows.

ObservationEvidenceWhy it mattersOption
Shared imports area codeThe access registry imports each area’s screen list, and shared/calc.ts imports the resource register.The shared layer cannot be reused or tested on its own, and import cycles become possible.Keep the registry as the one deliberate exception; move the clash calculation next to the resource code.
Helpers live in the wrong homeDownload and CSV helpers and a storage wrapper sit in talent/, another storage wrapper in tms/money/, and shared drawers and tabs in tms/money/ui.Areas depend on each other only to reach a utility.Move them into shared/; most cross-area edges in the matrix would disappear.
Many places write the main storeAbout 20 call sites use useStore.setState directly instead of a named action.Business rules are spread across components, so one change can be made in more than one way.Route writes through named actions, as tms/ops/mutate.ts and the resource actions already do.
One JavaScript bundleAll modules ship in a single 1797 KB file; every route is imported statically.First load downloads every screen, including areas a persona never opens.Lazy-load each area’s routes; the registry already groups screens by area.
Persona is global client statePersona lives in the main store, is persisted, and the guard switches it.Right for a demo; a real product would take identity from a session and enforce access on a server.Swap the persona source for an auth context and keep the registry as the permission model.
Data is one in-memory documentEach main-store action clones the whole data object.Cheap at demo scale, wasteful at production scale.Move to per-collection stores or an API with caching.
