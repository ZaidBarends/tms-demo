Training Platform: Architecture

The planned production architecture on Azure, drawn as a set of diagrams from one model. Companion to Demo architecture (as built), App flows and Process flows.

1. Status, notation and diagram index

This is the planned production architecture of the training platform on Azure. It is not a debate; items that are still open are drawn with a dashed outline and the words “to confirm”, and are listed in section 12. The frontend-only demo that exists today is described separately in Demo architecture (as built).

All names come from one model (the YAML in the source description), so the same thing has the same name in every diagram and table. Address ranges and resource names are proposals for IT to set.

Workbook is Deltek’s service, not ours. Deltek hosts and manages it, so nothing of Workbook runs in our Azure subscription or on our premises. Paths that do not go through the gateway

  • Sign-in. The browser talks to Microsoft directly: staff to Entra ID, everyone else to the External ID tenant (shown in D1 and D5). Tokens return to the browser, which sends them to the platform on N1.
  • Embedded reports. The browser loads report content from the Power BI service using an embed token the platform issued to confirm. It is drawn in D4 as the dashed lines from staff and client contacts to Power BI.
  • Administration. IT and the pipeline use the Azure management endpoints (Azure Resource Manager), not the gateway.

Network security group rules

  • snet-appgw accepts inbound 443 and 80 from the internet, and the gateway management ports 65200-65535 from the GatewayManager tag, as Application Gateway v2 requires.
  • snet-pe accepts inbound only from snet-appgw, snet-app and snet-func.
  • snet-app and snet-func accept no inbound traffic from the internet.

6. Identity and authorisation (D5)

Two Microsoft identity services prove who a person is; the platform’s own database decides what that person may do.

IDServiceWho signs inWhat the token carries

The platform is registered in both (reg-web-workforce, reg-web-external) and accepts tokens from either, recording the issuer with the user’s object ID.

Entra groupApp role
SG-TP-AdministratorsAdministrator
SG-TP-FinanceFinance
SG-TP-InstructorsInstructor
SG-TP-Staff-LearnersInternal learner

Flow A1, staff sign-in

  1. The browser requests a page; app-web finds no session and redirects to id-workforce (OpenID Connect, authorization code with PKCE).
  2. Entra applies Conditional Access, including multi-factor sign-in, then issues a token with the user’s app role.
  3. The browser returns to app-web with the code; app-web exchanges it and validates issuer, audience and signature.
  4. shared-access loads the user record and builds the request context: user, organisation (always the company itself for staff) and role.

Flow A2, external sign-in

  1. The browser is redirected to id-external, which runs the sign-up or sign-in flow.
  2. The token proves identity only. app-web validates it as above.
  3. shared-access looks up the membership record (user, organisation, role) in st-sql. No record means no access; a recruiter whose approval is pending also gets none.
  4. The request context is built from that record.

Authorisation on every request

  1. Token validation.
  2. Role policy: may this role use this area?
  3. Organisation and record check: does this record belong to the caller’s organisation, or to the caller?
  4. Row-level security: before running queries, the app sets the caller’s user, organisation and role in the SQL session context, and Azure SQL filters rows again.
  5. Audit: sensitive actions write a line to the audit table.

Recruiter path. app-talent validates the same external token, requires the Recruiter role with approved status, and connects to SQL as id-tp-talent, which can read only the anonymised talent view. In D5 the “Client identity providers (release 2)” box is optional and unconfirmed. Where External ID keeps its data is to confirm.

8. Ringfencing and talent search (D7)

The rule is enforced in the database, not in screens. The view returns only learners who are opted in and not withdrawn, built only from enrolments whose payer type is “self”, with no names or contact details. 9. Payments, invoice reference and Workbook integration (D11, D8)

Payments are taken by two South African processors: PayGate for cards, on a hosted payment page, and SnapScan for QR-code and app payments. They share one rule: the invoice number is the payment reference. It goes out with every payment request and comes back with the notification, so the platform always knows which invoice, and therefore which person or company, a payment belongs to.

How a payment is identified

QuestionRule
What is sent as the reference?The invoice number, for example INV-0042, in the format set by the numbering settings. It is sent in PayGate’s reference field and SnapScan’s merchant-reference field to confirm field names and length limits.
Where does the invoice come from?B2C: the invoice is raised at booking, before payment, with payer type “self”. B2B: the existing invoice, paid from the client’s invoice screen. Finance can also send a pay link or QR code for any open invoice.
What does the payer see?The invoice number and amount on the payment page, on the receipt and in the confirmation email.
What must a notification carry?Invoice number, amount, the processor’s transaction id, status and a signature or checksum that the platform verifies.
How is the payer known?From the invoice: its organisation (B2B) or learner (B2C). The payment is stored against that invoice, so “who paid what” is a lookup, not a guess.
How is a repeat avoided?The idempotency key is the processor plus its transaction id. A repeated notification changes nothing.
Can a payer try again?Yes. Each try is a separate payment attempt on the same invoice. If a processor rejects a repeated reference, a short attempt suffix is added and stripped when matching to confirm.

What happens to each notification

NotificationResult
Valid, invoice found, amount equals the balancePayment recorded, invoice settled, booking confirmed (B2C), event sent to Workbook.
Valid, invoice found, amount is less than the balanceRecorded as a part payment; the invoice stays open with the new balance.
Valid, invoice found, amount is more than the balanceInvoice settled; the excess is flagged for Finance to refund or credit.
Valid, invoice already paidRecorded and flagged as a duplicate payment for refund.
Invoice number missing, unknown or alteredHeld in the unmatched queue; an alert goes to Finance; nothing is settled until a person allocates it.
Signature or checksum invalidRejected with an error; alert raised.
Same transaction id againIgnored: no change.

The payment record

FieldHolds
Invoice numberThe reference sent and returned; links to the invoice, and through it to the organisation or learner
Processor and transaction idPayGate or SnapScan, and its own id (the idempotency key)
MethodCard or SnapScan (bank transfer is recorded separately)
Amount, status, received atAs reported by the processor and confirmed against the invoice balance
Notification logThe raw notification, kept for audit
Workbook referenceSet when the payment has been posted to Workbook

Payment methods

MethodHow it works
CardThe learner or client is sent to PayGate’s hosted payment page; card details never reach the platform. PayGate notifies the platform and returns the browser to the site, which checks status until the notification is processed.
SnapScanThe payment page shows a QR code (a link on a phone) carrying the invoice number and amount. The payer scans it in the SnapScan app; SnapScan notifies the platform.
Bank transfer (EFT)The payer quotes the invoice number as the bank reference. Finance confirms it from the bank record in Workbook, and the worker reads payment status from Workbook. Whether PayGate or SnapScan will also carry EFT is to confirm.
RefundsMade through the processor for card and SnapScan payments, referencing the invoice and any credit note to confirm.

Payment and invoice to Workbook

Four things make the integration safe: the event is written with the business change in one transaction, the worker retries from a queue, a message that keeps failing waits in a dead-letter queue where a person can see and resend it, and nightly and daily comparisons (Workbook, and the processors’ settlement reports) record any drift, by invoice number. A payment is posted to Workbook only after its invoice has synced.

10. Environments and release pipeline (D9)

Three environments share one layout and differ in size and protection. Each has its own subscription, resource groups, identities and data; names carry a suffix of dev, stg or prod.

EnvironmentSubscriptionEntry pointSize and resilienceData
Developmentsub-tp-devApplication Gateway optional; may use restricted direct accessSmall tiers, one zone, may be switched off out of hoursSynthetic or masked
Stagingsub-tp-stgApplication Gateway WAF v2, same rules as productionSmaller than production, one zoneMasked copy
Productionsub-tp-prodApplication Gateway WAF v2, zone-redundantZone-redundant, backups, alertsReal
  1. A developer opens a pull request in the repository (GitHub or Azure DevOps, to confirm; drawn as one generic box); a second person must review it.
  2. On merge the pipeline builds once, runs tests and scans dependencies, producing one artefact.
  3. The pipeline deploys the artefact to development, then to staging, automatically.
  4. An approval gate holds production. Approvers: the product owner and an IT operations approver; the finance lead also approves releases that touch the Workbook link.
  5. Production step 1: the database migration runs under id-tp-migrate. Step 2: the artefact deploys to the staging slot of app-web and app-talent. Step 3: health checks at /healthz and smoke tests run against the slot. Step 4: the slot is swapped into production. If a check fails afterwards, swap back.

Infrastructure changes use templates in a separate repository. The pipeline shows the planned change, IT reviews it, then it applies. The pipeline signs in with a federated identity, wif-pipeline, so it stores no password. Development may skip the Application Gateway; D3 and D4 draw production.
